# 竞品调研笔记(2/3):Orca(stablyai/orca)—— agent 的 IDE,worktree 即基本单元

> 调研日期:2026-07-31。取证方式:GitHub README/docs 源码 + 官网文档站(onorca.dev)+ GitHub API + 第三方分析交叉验证。事实均标注来源;「推测」处单独标明。

## 产品速览

- 定位:ADE(Agent Development Environment),"The AI Orchestrator for 100x builders"。Electron 桌面(macOS/Windows/Linux)+ iOS/Android 伴侣应用 + headless 服务器模式(`orca serve`),MIT 开源,YC 背书。来源:[README](https://github.com/stablyai/orca)
- 活跃度(GitHub API,2026-07-31):34.1k stars / 2.4k forks / 2.7k open issues;仓库 2026-03-17 创建(仅 4.5 个月),调研当天仍在密集 commit,README 自称 "we ship daily" 名副其实。推测:repo 内有 `star-nag` 求 star 功能,star 数可能有运营水分。
- 技术栈:TypeScript + Electron + React + xterm.js(含 headless)+ node-pty + WebSocket + SQLite(orchestration db)。来源:[package.json](https://github.com/stablyai/orca/blob/main/package.json)
- Agent 中立:README 列 30+ 家(Claude Code、Codex、Kimi、Grok、OpenCode……),抽象层是"任何跑在终端里的 CLI"。

## 核心机制拆解

**进程模型(官方文档写明)**:经典 Electron 三段 + `src/cli` 和 `src/relay` 两个一等子系统;另有庞大的本地 PTY daemon 子系统(`src/main/daemon/`,60+ 文件:headless xterm 终端模型、空闲关闭、宿主迁移、健康检查)。执行层权威分三层:Client/renderer(发意图)→ Runtime/controller(Electron 主进程,签 claim)→ **Execution owner(daemon 或 relay,唯一能原子回答"这个 agent 会话是否已有存活 PTY"的最底层进程)**。来源:[remote-agent-session-host-authority.md](https://github.com/stablyai/orca/blob/main/docs/reference/remote-agent-session-host-authority.md)、[src/main/daemon](https://github.com/stablyai/orca/tree/main/src/main/daemon)。CLI 是一等公民(`worktree ps/create/rm`、`terminal list/read/send/wait`、`orchestration ...`),走 Unix socket / named pipe / WebSocket,`--json` 面向脚本——**设计意图是 agent 自己也能驱动 Orca**。

**会话持久化(官方写明)**:host-owned 模型——所有 PTY 字节先进主进程/daemon 维护的有界 headless xterm 模型,renderer 只是 view;有磁盘 checkpoint/增量恢复,但**官方明确"这不是无限 transcript"**。来源:[terminal-main-owned-state.md](https://github.com/stablyai/orca/blob/main/docs/terminal-main-owned-state.md)。关键协议 `terminal.ensureAgentSession`:以 provider 会话身份(Claude Code `session_id` / Codex `conversation_id`)为键做原子 claim-or-spawn,冲突时 **fail closed 不 spawn**,不变量 = "一个 provider 会话身份在任何 route 上至多一个存活 PTY owner";另有 hibernation/cold-restore(休眠 workspace)。关 app 后会话分场景:远程(SSH/serve)**在**(relay 租约默认 5 分钟宽限保 PTY);移动端**断**(无云 relay);本地场景官方未明确承诺进程存活,推测 = scrollback/元数据/provider 会话 ID 持久,重开靠 ensureAgentSession resume。

**git worktree 隔离(官方写明,三家最深的实现)**,来源:[Worktrees 文档](https://www.onorca.dev/docs/model/worktrees):
- 模型三要素:每 repo 一个 base ref;每 worktree 一个 start-from ref;独立分支 + 独立目录 + 独立 agent 终端。分支名从 workspace 名 slug 化或从 GitHub PR / Linear / Jira / GitLab MR 派生。
- 生命周期:Create(后台 fetch + worktree add,可并行可取消)→ Work → Review(对 start-from ref 的 diff)→ Ship(app 内 commit → push → 开 PR → 等 CI)→ Archive/Sleep/Delete。**merge 走标准 PR + CI,Orca 不做自动 merge**。
- 落地三件套(最先踩的坑已有成熟答案):新 worktree 没有 gitignored 的 `node_modules`/`.env`,Orca 给三层补齐——① repo 级 Worktree Shared Paths(APFS clone/symlink);② `orca.yaml` 的 `worktree.sharedDirectories`(入库共享);③ 根目录 `.worktreeinclude`(拷贝 `.env` 类)。
- **重要边界(第三方指出,官方可佐证):worktree 是文件/git 隔离,不是安全沙箱**;Orca 默认给 agent 加跳过权限确认参数(`--dangerously-skip-permissions`/`--yolo` 系),需手动改回 Manual。来源:[piglife.tw 分析](https://piglife.tw/technical-notes/orca-parallel-ai-coding-agent-worktrees/)

**relay 与断线重连(官方写明,对既有认知的最大修正)**:**relay 是宿主侧组件,不是云服务**。SSH 模式首次连接自动在远端装小 relay;VPS 模式 `orca serve` 跑 headless(systemd 托管)。移动端配对码直连桌面,**无云 relay**——桌面关掉手机就断,重开自动重连;远程可达靠 LAN/Tailscale/反代。断线语义:SSH 断不杀 agent;relay 租约 5 分钟宽限(可配)保 PTY;端口转发跨重连持久;重连一致性靠 host-authority 协议(operation ID 24h 去重、claim digest、进程 incarnation 校验)保证"重试不产生第二个进程"。E2EE 配对。来源:[SSH docs](https://www.onorca.dev/docs/ssh)、[mobile docs](https://www.onorca.dev/docs/mobile)、[headless-linux-server.md](https://github.com/stablyai/orca/blob/main/docs/reference/headless-linux-server.md)、[src/relay](https://github.com/stablyai/orca/tree/main/src/relay)

**agent 间消息/编排(官方写明,2026-07 集中落地,超出预期)**,来源:[ORCHESTRATION_IMPLEMENTATION_CHECKLIST.md(107KB)](https://github.com/stablyai/orca/blob/main/ORCHESTRATION_IMPLEMENTATION_CHECKLIST.md):
- 两层机制:① 临时消息层 `orca orchestration send --to @claude`,`@group` 地址按终端标题 token fan-out;② **结构化原语层:Run / Task / Dispatch / Message**——Run = 持久命名空间 + 权威 home mailbox,显式绑定一个 **coordinator pane**(就是个普通 agent 终端);`worker-start/stop/abandon` 由 coordinator 用 CLI 组合式创建 worker(可选新 worktree、可选 `--on <远端>` 放到另一台 Orca server = federation);Dispatch 状态机完整(starting/ready/succeeded/failed/stopping/stopped/abandoned);崩溃安全 inbox(FIFO 批次、单 outstanding delivery、幂等 ack、跨重启保留)。
- 安全:每 Dispatch 注入 256-bit capability(只存 SHA-256 verifier);worker 上报标注 `worker_report` provenance——**Orca 明确不为 worker 自报的正确性背书**。
- **明确非目标:不做调度器、容量分配、自动重试、UI dashboard——"Agents choose decomposition, topology, placement, parallelism, and recovery strategy"**。策略归 agent,机制归平台。

**diff review(官方写明,人是 reviewer)**,来源:[Annotate AI Diff](https://www.onorca.dev/docs/review/annotate-ai-diff):diff 任意行 hover 写 markdown 评论,钉在精确行上并随 diff 移动;审完 **Send to agent**——所有评论合成**一条**带行锚点的 prompt 发给 agent 修订(官方解释批量原因:逐条发会让 agent 来回摆动,批量保证"一轮思考、一轮修订");评论在修订后保留供验证,可 Resolve。配套 Attribution(每段改动出自哪个 agent/人)。

**任务管理**:不自建看板,原生集成外部任务系统(GitHub/Linear/Jira/GitLab/Azure DevOps/Bitbucket/Gitea),任何 task 一键开 worktree;agent 侧另有 Run/Task/Dispatch 内部任务模型。

## 值得抄的

1. **三层进程模型 + "一个 provider 会话身份至多一个存活 PTY owner" 不变量 + fail-closed**——断线重连正确性的核心,远比"重连后恢复 UI"难也重要。
2. **worktree 落地三件套**(shared paths / sharedDirectories / .worktreeinclude)——worktree 方案最先踩的坑的成熟答案。
3. **编排原语最小集**(Run/Task/Dispatch/Message + crash-safe mailbox + capability 注入)且"策略归 agent、机制归平台"——checklist 本身就是一份极好的需求清单。
4. **relay 放远端、租约保活、无云中转**——与 Herdr 的 SSH 思路同构,5 分钟宽限期这种小数字是体验分水岭。
5. **批量行锚点 review → 一条 prompt 修订**——"一轮思考、一轮修订"的交互细节。

## 要避开的坑

1. Electron 单体重量(`orca-runtime.ts` 单文件 1.3MB,2.7k open issues 是功能速度的代价)。
2. **默认 `--yolo` 系权限策略**——并行 fleet + 默认跳过权限确认,事故只是时间问题。
3. worktree ≠ 安全沙箱,别把 git 隔离当安全边界宣传。
4. star-nag 式增长手段;移动端是 read-mostly 遥控器,别指望完整工作流。

## 两个差异化洞察在 Orca 身上差多远

**洞察一(中控 agent 一等公民):半成品,且是三家最近的。** 有 coordinator 概念——Run 显式绑定一个 coordinator pane,它就是普通 agent,靠 orchestration CLI/skill 获得编排能力(worker-start/stop、mailbox、federation)。**能力是协议给的,不是实体给的**:coordinator 没有专属的全局上下文管理、没有台账/ledger 概念、没有"持续在岗"的驻守语义(它是被 prompt 唤醒干活的普通 agent),平台还明确把调度策略让渡给 agent 自己。离 Collie 的"读台账、拆任务、复核产出的常驻 lead"差的是角色定义 + 全局上下文载体。

**洞察二(分级复核成本结构):半成品。** diff review 内建且交互精良,`worker_report` provenance 标注(平台不为自报背书)是复核凭据意识的萌芽——但 **reviewer 是人不是 agent**,无风险分级门禁、无"凭证据复核而非重跑"的机制,复核成本全在人身上。

**一句话结论:Orca 把"工作区隔离 + agent 编排机制"做成了平台级原语(worktree 三件套、PTY owner 不变量、Run/Dispatch/mailbox),但它刻意把策略和复核都留给 agent 和人——Collie 的中控角色与分级复核正是它留白的地方。**

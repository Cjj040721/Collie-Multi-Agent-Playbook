# 竞品调研笔记(3/3):Multica —— agent 当队友的平台,严谨的后端契约集

> 调研日期:2026-07-31。取证方式:本机 `multica` CLI(v0.4.15)全量 help 文本 + daemon 日志/工作目录实证 + 官方注入式 skill 文档(标注 server 源码 file:line)+ 官网/GitHub/官方文档站 + 第三方报道。标注方式:【CLI】【日志】【skill文档】【官方文档】【README】【第三方】【推测】。

## 产品速览

- 定位:开源 "managed agents platform",把 coding agent 变成看板上的一等队友——分派 issue、跟踪进度、沉淀 skill。名字 = **Mul**tiplexed **I**nformation and **C**omputing **A**gent,致敬 Multics。【[README](https://github.com/multica-ai/multica)】
- 核心差异化:**agent 不跑在 Multica 服务器上**——跑在用户自己机器上,由本地 daemon 驱动本地已装的 AI CLI;server 只做协调(存 issue、排队、派发)。API key、工具链、代码目录都不出本机。【[官方文档 daemon-runtimes](https://www.multica.ai/docs/daemon-runtimes)】
- 支持 17 种 agent CLI(Claude Code、Codex、Kimi、OpenCode、Cursor、Copilot、Grok……)。技术栈:Next.js + Go(Chi/sqlc/websocket)+ PostgreSQL 17(pgvector)+ daemon;另有 desktop app(内嵌 daemon)和 iOS app。【README】
- 开源:Apache 2.0 文本 + 附加条件(托管服务/商业分发需商业授权;UI 保留品牌标识)。自托管免费(Docker 一键);Cloud 有免费层,cloud runtimes(免本地 daemon)还在 waitlist。【README License 段;[第三方](https://flowtivity.ai/blog/multica-vs-paperclip-vs-claude-managed-agents-comparison/)】

## 核心机制拆解

**进程模型(官方写明 + CLI 实证):云控制面 + 本地执行面。**
- Runtime = daemon × 一个 AI 工具;daemon 启动做四件事:读凭证 → 扫 PATH 上 17 种内置工具 → 向 server 注册 → **每 3 秒 poll 任务、每 15 秒 heartbeat**。【官方文档;CLI `daemon start --help`】
- 任务派发链(source-traced 契约):用户动作在 server 写 `agent_task_queue` → server 尽量经 daemon websocket 主动唤醒 → daemon poll/claim → server 返回任务上下文(repos、project resources、**prior session/workdir hints**、task token)→ daemon 准备 workdir 并启动 provider CLI。【skill文档 multica-runtimes-and-repos】
- 触发 run 四途径:分派 issue、评论 @mention agent、chat 消息、autopilot。task 状态机 `queued → dispatched → running → completed/failed/cancelled`;超时:dispatched 未启动 5 分钟、running 超 2.5 小时(一刀切)。并发双层限流:daemon 默认 20、agent 默认 6。【[官方文档 tasks](https://www.multica.ai/docs/tasks)】
- agent 配置:`instructions`(claim 时注入 provider 的持久行为契约)、`model`、`thinking_level`、`custom_env`/`mcp_config`(密钥级,agent actor 一律拒读明文)、`permission_mode`。【CLI `agent create --help`】

**会话/上下文持久化(官方写明 + 推测综合)**:
- 单任务内:任务开始(收到首条 system 消息)和结束各 pin 一次 session ID——前者用于 daemon 崩溃恢复,后者用于自动重试/按行重试时接着上次对话继续;**若失败"污染"了会话(context overflow、迭代上限等),则只复用 workdir、开新会话**。workdir 复用与 session resume 是两个独立维度。【官方文档 tasks】
- **跨任务:没有 agent 长期记忆**【推测:综合多处证据,官方未单页声明】。新任务默认全新 session/workdir,记忆靠四样 durable 载体手动重建:① `instructions`;② workspace skills;③ issue 评论线程 + metadata KV(`pr_url`/`waiting_on`/`blocked_reason`/`decision` 等推荐键);④ chat 频道历史。每个任务目录有 `.multica/daemon_task_context.json` + `.agent_context/issue_context.md` 冷启动。【本地实证】

**隔离实现与产出回流(CLI + 日志实证 + skill文档)**:
- 每任务一个独立目录 `~/multica_workspaces_<profile>/<workspace-id>/<task-id前8位>/`;**repo checkout = 从 daemon 的 bare clone 缓存建 git worktree**,分支命名 `agent/<agent名>/<task-id前8位>`。例外:Linux 上 Codex 用 task-local git metadata 以配合它的 sandbox。【CLI `repo checkout --help`;daemon 日志】
- daemon 有 GC(定期删 stale agent 分支)+ `daemon disk-usage` 可查磁盘。【日志;CLI】
- **产出回流 = GitHub PR 链路,合并门禁完全在 GitHub 和人手里**:PR 标题/正文/分支名含 issue key 即被 webhook 关联;`Closes/Fixes MUL-xxx` 紧邻 key 才记 close intent(PR merge 自动把 issue 推 done),松散提及标 `reference_only` 并隐藏。Multica 自己不 merge、不设门禁。【skill文档 multica-working-on-issues】

**relay/断线重连(官方写明)**:通信 = 3s 轮询 + websocket 主动唤醒 + 15s 心跳;45 秒(3 拍)无心跳标 missing,恢复即回 online。**missing 时的在跑任务标 `failed(runtime_offline)` 自动重排队;daemon 崩溃重启主动告知 server 标 `failed(runtime_recovery)` 并重排,server 30 秒扫描兜底**。重试分类学:retryable(offline/recovery/timeout)最多 2 次;`agent_error`(API 错误/配额)不重试——重试只会死循环;autopilot 任务不自动重试(避免与下一次调度重叠)。【官方文档 daemon-runtimes/tasks】

**agent 间消息/编排(官方写明,最厚的部分,全部 source-traced)**:
- **@mention 即编排**:`mention://agent/<uuid>` → enqueue run;`mention://squad/<uuid>` → 解析出 leader、给 leader enqueue;`member`/`issue` → 纯链接不触发。`@all` 广播不触发任何 agent 且抑制 assignee 自动触发。静默 no-op 集:错 UUID、目标已有 pending task(去重)、archived、无权访问——全部静默跳过防循环。【skill文档 multica-mentioning,源码 comment.go】
- agent 可用 CLI 创建 issue、分派、建子 issue、发评论、改状态——**agent 驱动 agent 是一等能力**。
- **autopilot** = 定时(cron + IANA 时区)/webhook/手动触发的自动化规则(不是 agent),两种模式:`create_issue`(建 issue 路由给 agent/squad)或 `run_only`(直接建 task)。webhook 入口有 durable 队列 + 幂等 delivery key。【CLI;skill文档 multica-autopilots】
- **squad = 路由与协调对象,不是 agent、不会自己跑**:分派/评论/@mention/autopilot 全部路由到 `leader_id` agent,**不做成员 fan-out**;member `role` 只是花名册标签,不产生调度/权限。【skill文档 multica-squads】
- **子 issue 与 stage 屏障**:`--stage N` 把子 issue 编成有序屏障组——一个 stage 内全部终态后,server 唤醒父 issue assignee **一次**,由它决定提升下一 stage;推进是 agent 驱动的,server 只检测屏障闭合。【CLI `issue create --help`;skill文档】

**skill 系统(CLI + skill文档)**:workspace 级 DB 行(SKILL.md + supporting files,整包 8MiB 上限);`skill import --url` 支持 clawhub.ai、skills.sh、GitHub 三种形态;skill 与 agent 显式绑定,claim 时 daemon 按 provider 原生发现路径注入(Claude→`.claude/skills/`、Kimi→`.kimi/skills/` 等)。官方叙事是"skill compounding",但**沉淀动作靠 agent/人主动 create,无自动提炼机制**【推测】。

## 值得抄的

1. **任务派发链的权责切分**:server 只管队列+状态机+路由,执行面全在本地 daemon——"密钥和代码不出本机"是极强卖点,也天然回答了排障路径。
2. **mention 即编排协议**:把"agent 驱动 agent"变成纯文本契约,四类型语义清晰,静默 no-op + pending 去重防循环,非常克制。
3. **squad leader briefing**:leader 拿到的花名册**带每个成员的 skill 清单**——按能力委派,比"@FrontendTeam"口号实在。
4. **stage 屏障**:server 只检测"一组子 issue 全部终态"并唤醒父 assignee 一次——编排骨架系统保证、节奏 agent 掌握。
5. **失败分类学**:retryable vs agent_error 不重试 vs autopilot 不自动重试,每类都有明确理由;session 双 pin + "会话被污染则只复用 workdir"的降级设计很细。
6. **PR link 与 close intent 两次扫描分离**,松散提及标 `reference_only` 隐藏——避免无关 PR 冒充工作产出。
7. skill 按 provider 原生发现路径注入(而非自造协议)+ 导入生态。

## 要避开的坑 / 空档

1. **squad 不做 fan-out、role 只是标签**——squad 实质是"leader 单点路由",成员自动并行缺失。
2. **跨任务无 agent 长期记忆**——全靠 instructions+skills+评论+metadata 手动重建。
3. **review 没有内建机制**——`in_review` 靠 agent 自觉翻、done 靠人或 PR close intent;无 reviewer 角色、无"交付必须经谁复核"的门禁。
4. **合并门禁完全外包 GitHub**——不用 GitHub 的团队(如 Perforce 用户,[Discussion #4298](https://github.com/multica-ai/multica/discussions/4298))整套链路失效。
5. 超时偏粗(running 一刀切 2.5h);autopilot 失败后只通知不自动重试。
6. **协议不够自解释**:mention UUID、close intent 邻接规则、todo vs backlog 触发语义……官方要专门写一批注入式 skill 文档 + Go 行为测试教 agent 别犯错。设计契约应"错不了"而不是"教得会"。

## 两个差异化洞察在 Multica 身上差多远

**洞察一(中控 agent 一等公民):半成品,三家最近。** squad leader 是被 briefing 武装的 lead agent——有花名册(带成员 skill 清单)、有对父 issue 的状态权(首次 dispatch 推 in_progress,确认整体目标达成才推 in_review)、有 `squad activity` 把评估决策写回时间线。但 leader 是**被触发才上岗**而非**持续在岗读台账**:无跨任务记忆,全局上下文靠 instructions + 评论线程 + metadata KV 手动重建,"读台账了解全局"这个动作的成本全部压在每次冷启动上。离 Collie 的常驻中控差的是:持久化的全局上下文载体(台账即系统)+ 在岗驻守语义。

**洞察二(分级复核成本结构):完全没有到萌芽。** `in_review` 靠 agent 自觉翻、done 靠人或 GitHub PR close intent;无 reviewer 角色、无风险分级门禁、无"复核凭据而非重跑"的机制。合并门禁完全委托 GitHub 分支保护——这不等于分级复核,只是把复核问题整个外包了。

**一句话结论:Multica 把"agent 当队友"做成了严谨的后端契约集(队列状态机、mention 触发图、squad 路由、stage 屏障、PR 回流),执行面彻底本地化换取信任;它弱在 agent 长期记忆、真并行 fan-out 和内建 review 门禁——这三处正是 Collie 的潜在空档。**

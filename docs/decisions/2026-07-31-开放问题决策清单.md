## 1. 中控 agent 的上下文如何持久化与交接?

现状:靠 md 快照,有明显局限;现行做法是「任务卡冷启动 + LEDGER 唯一真相源」,不做全量上下文常驻(那是第一时代烧 token 的死法)。

- **A. 维持 md 文档栈**(三件套 + 任务卡 + NOW 交接条目):零新增成本、已在四个项目验证、人可读;短板是检索弱,项目多了之后中控冷启动要读的东西线性增长。
- **B. 结构化存储**(YAML/JSON/SQLite):机器可靠读写、可校验、可查询;短板是人可读性下降,且格式要先冻结——现在连工作模式都还在演进,冻结太早。
- **C. 混合分层**:md 仍是给人和冷启动用的主载体,在此基础上逐步把「需要被程序消费的部分」收紧为可机读字段(LEDGER 的 `日期|编号|内容|commit|证据` 已经是半结构化)。

**建议倾向:C。** 工作模式层先维持 md 纪律,把结构化收紧做进 `LEDGER-规范.md`(见第 4 条);「台账即系统」是 Collie 产品层的答案,等产品化时再选存储技术。现在选 B 属于过早优化。

## 2. 复核的 token/时间成本预算怎么定?风险级由谁划定?

现状:L1/L2/L3 三级门禁已在 `通用工作流.md` §五定稿,风险级现行由人派活时标注,规则是「拿不准就升一级」。

**风险级划定:**

- **A. 人拍板,中控只执行**(现行):最简单可控;短板是人是瓶颈,派活一多标注质量会敷衍。
- **B. 中控自判,人抽检**:省人;短板是中控有自我放松的结构性风险(自己定的级自己复核,等于没门禁)。
- **C. 人定规则与红线,中控按规则分类,只能升不能降**:红线清单不变(钱/数值/公式/对外一律 L3),其余由中控按判据表定级,人保留改级权。

**建议倾向:C。** 它把人的工序从「逐条标注」压缩到「维护规则表」,符合「瓶颈是人的工序」这条核心认知;「只能升不能降」堵住自我放松。

**成本预算:**

- **A. 设数字上限**(如复核 token ≤ 执行 token 的 X%):可量化;但现在没有基线数据,拍出来的 X 是空对空。
- **B. 按风险级自然封顶,先不设数字**:L1 成本≈0、L2 只看 diff、L3 才复跑,成本结构本身已经是预算;把实际复核成本记进 `工具观察笔记.md`,观察 2~4 周后再决定是否要数字上限。

**建议倾向:B。** 第一时代的教训是「全量上下文 + 每步全量复核」,分级门禁已经把这个成本结构拆掉了;先用观察数据说话,别拍脑袋定数字。

## 3. 哪些复核必须留给人?

现状(`通用工作流.md` §一 + `工具观察笔记.md` Multica 实战):UI/文案人亲眼看;真机体验、用户试用永远人做;Multica 试点印证了「推不推、合不合(git 决策)仍是人的门禁」。

- **A. 最小红线(现行)**:UI/文案视觉 + 真机体验 + 对外发布内容。其余全部走分级门禁。
- **B. 扩展红线**:A + git 合并/推送决策 + 涉及真实用户数据与付费的任何变更。
- **C. 逐项目自定义**:每个项目在自己的 AGENTS.md 里定红线。灵活,但通用工作流就失去默认值,新项目容易漏。

**建议倾向:B。** Multica 实战已经证明 git 决策留在人手里是正确分工;真实用户数据/付费与 `通用工作流.md` §五「一律 L3」的精神一致。建议把这五条写成明确清单补进 `通用工作流.md` §一,而不是散落在各处。

## 4. 台账结构化成什么样,才能既被 agent 可靠读写、又对人可读?

现状:`LEDGER-规范.md` 已是一行一条的半结构格式(固定分隔符 + 必填 commit + 证据原文);规范明确「宁粗勿缺,首先写给下一个 session 的 agent 看」。

- **A. 维持现状**:够用、零成本;但「可靠读写」靠约定不靠校验,agent 写歪了没人发现。
- **B. 轻量收紧**:不改 markdown 载体,只把字段收紧为可正则解析——风险级/状态改枚举值、commit 号格式校验、证据字段必填项明确化。可以加一个极简 lint 脚本做校验。
- **C. 迁数据库/YAML**:最可靠;但背离「对人可读、维护成本低到不可能脱节」这条立身之本,灵修伴读的计划文档就是这么死的。

**建议倾向:B。** 它是「台账即系统」构想的最小可行一步:先让现有格式可被程序校验,验证 agent 读写的可靠性;DB 是 Collie 产品化阶段的技术选型问题,不是现在的问题。

## 5. Collie 的形态:TUI / 桌面 GUI / 两者结合?

现状:已定「工作模式先行,app 缓建」;owner 是终端重度用户(herdr spaces 挂 10+ 工作区);`工具观察笔记.md` 给 Orca 标了「Electron 重量」的待验证顾虑;Multica 的 CLI 全覆盖被记为爽点。

- **A. TUI/CLI 优先**:贴 owner 现有工作流、可脚本化、开发成本低;天花板是总览/dashboard 和 diff 复核的可视化体验。
- **B. 桌面 GUI 优先**:总览与复核体验上限最高;开发成本最高,且现在需求未定型,先造 GUI 等于先冻结交互再反推需求。
- **C. CLI/daemon 内核 + 薄视图层**:核心能力(台账即系统、分级复核流程、任务分派)做成无头服务 + CLI,GUI/TUI 都只是视图;先 CLI 跑通,视图后补。

**建议倾向:C。** 理由:① Multica 实战已经证明「CLI 全覆盖」这条路对工作流的价值最大;② 它兼容「工作模式先行」——模式先跑成脚本,壳后长出来;③ 视图层是 TUI 还是 GUI 可以推迟到需求定型后再拍。**注意:这是远期架构方向,不构成启动开发的理由。**

## 6. 目标用户:先 dogfooding,还是一开始就当产品做?

现状:`Collie-项目初想.md` 当前决策已隐含答案——「工作模式先行,需求素材从真实使用中长出来」。

- **A. 纯 dogfooding**:需求绝对真实;风险是只有一个用户,长不出通用产品。
- **B. 一开始当产品做**:有市场约束;但需求未验证就定型,正是本仓库要避免的。
- **C. dogfooding 先行 + 产品化检查点**:维持 A,但设定期检查点(如每次季度复盘)回答「这套模式里哪部分对别人也有用」,达到阈值再开放给第二批用户。

**建议倾向:C。** 实质是把已定决策补上检查点机制,防止 dogfooding 无限期滑行;检查点挂到周复盘机制上,零新增流程。

## 7.【计划外新增】Collie 的基本组织单位:单项目纵深,还是多项目舰队?

依据:`Collie-项目初想.md` 功能想象里写了「多项目工作台/项目舰队」,但开放问题清单漏了对应的决策点;owner 的工作天然是多项目并行(herdr spaces 10+ 工作区,四条主线)。

- **A. 单项目纵深**:把一个项目内的「中控 + worker + 台账 + 复核」做透,多项目靠开多个实例。简单;但 owner 的核心痛点(跨项目总览与切换)没被解决。
- **B. 多项目舰队为一等公民**:基本单位就是「项目舰队」,每个项目有自己的台账/中控状态,一个界面总览切换。贴合真实工作模式;复杂度高。

**建议倾向:B,但作为产品层的方向性确认,不影响阶段一后续工作。** 理由:owner 自己的工作形态就是舰队(四条主线 + 10+ 工作区),herdr spaces 和 Kimi Work 工作台的价值都被验证过;单项目纵深可以作为舰队的一个特例自然成立,反过来不行。
